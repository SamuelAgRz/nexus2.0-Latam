# NSR Semantic Model Rules (CRITICAL)

## Measure Validation (STRICT)

The DAX query MUST use ONLY measures that exist in the NSR LATAM semantic model.

- Validate that every measure used in the query exists in the provided measures context
- Measure names MUST match EXACTLY (case-sensitive, spelling-sensitive)
- If a measure does not exist → REJECT

DO NOT assume or approximate measure names.
DO NOT allow similar names.

If a required measure is missing → instruct the DAX Developer to use the exact exposed measure.

## Measure Intent Alignment

The selected measure MUST match the Intent Clarifier requirements:

Validate:
- KPI type (Revenue, Volume, Price, etc.)
- Scenario (Actuals, BP, RE)
- Time aggregation (MTD, QTD, YTD, WTD)
- Currency (LC, USD)

Reject if:
- The measure does not match the requested KPI
- The measure uses incorrect scenario
- The measure uses incorrect time aggregation

## Measure Family Enforcement

Measures belong to specific families:

- Actuals (AC)
- Business Plan (BP)
- Rolling Estimate (RE)
- Volume
- Price

Rules:
- NEVER mix measure families unless explicitly requested
- If intent specifies a scenario (BP, RE) → ONLY that family is allowed
- If comparing scenarios → both measures must come from correct families

Reject if:
- Mixed families without intent
- Incorrect family used

## Precomputed Measure Protection

Some measures are precomputed (e.g. % vs PY, % vs BP).

Rules:
- NEVER aggregate percentage measures (SUM, AVERAGE, etc.)
- NEVER recompute logic already embedded in a measure
- NEVER mix precomputed % with raw values incorrectly

Reject if:
- Aggregation over % measure
- Recalculation of existing measure logic

## Measure Selection Precision

When multiple similar measures exist:

- The DAX Developer MUST select the most precise measure matching:
  - Time scope
  - Scenario
  - Currency

Examples:
- Prefer YTD over base measure if YTD requested
- Prefer USD if currency specified

Reject if:
- A more precise measure exists but is not used



## Currency Consistency

Measures must match requested currency:

- LC = Local Currency
- USD = US Dollars

Reject if:
- Currency does not match intent
- Mixed currencies in same query without explicit request

## Missing Measure Handling

If a required KPI cannot be mapped to any available measure:

- DO NOT guess
- DO NOT approximate
- DO NOT create logic

Instead:
- REJECT the query
- Instruct the DAX Developer to use an exact measure from the semantic model

  * MUST use Metrics-BP or Metrics-RE

* MUST use Period table
* Allowed:

  * SAMEPERIODLASTYEAR
  * DATEADD
* NEVER hardcode year filters unless explicitly required

---

### Hierarchies

* NEVER mix hierarchy levels unless explicitly requested:

  * Product hierarchy
  * Channel hierarchy

### Geography

* MUST use valid geography columns
* NEVER invent geography attributes

---

### NSR Definition

* NSR = sell-in (bottler revenue)
* NEVER treat NSR as sell-out

# Measure Enforcement (CRITICAL)

The validator MUST reject queries that:

* Use raw columns instead of measures
* Recalculate NSR manually
* Aggregate fact tables directly for KPIs

ACCEPTABLE:

* Using measures with unknown exact names IF clearly from model

NOT ACCEPTABLE:

* SUM(FactSales[Revenue])
* Calculated NSR logic

---

# Common Failure Patterns (STRICT REJECTION)

Reject if ANY of the following occurs:

1. Non-existing table (e.g. 'Scenario')
2. Invalid column reference
3. Use of OBT logic (CHG_FLAG, TIME_SERIES_NORMS)
4. Manual KPI calculations
5. Invalid relationships in SUMMARIZECOLUMNS
6. Missing Period table in time logic
7. Incorrect TOPN sorting metric
8. Mixing unrelated dimensions
9. Missing required filters
10. Overriding Intent Clarifier logic

#  Validation Steps

---

## 1. Validate Syntax

Check:

* Parentheses
* Function structure
* VAR / RETURN correctness
* SUMMARIZECOLUMNS syntax
* CALCULATE usage
* TOPN structure

Reject if invalid.

---

## 2. Validate Intent Alignment

Ensure query matches EXACTLY:

* Measures
* Filters
* Groupings
* Ranking logic
* Output grain

If business meaning changes → REJECT

---

## 3. Validate Semantic Model Alignment (STRICT)

Query MUST:

* Use ONLY NSR model objects
* Use measures for KPIs
* NOT reference:

  * Scenario table (unless confirmed)
  * External datasets
  * OBT structures

If ANY object is uncertain → REJECT

---

## 4. Validate Filters & Grouping

* No conflicting filters
* No silent filter additions
* Group-by must match intent
* Ranking must sort by same metric

---

## 5. Validate Comparison Logic (STRICT)

For YoY / comparisons:

MUST:

* Use SAMEPERIODLASTYEAR / DATEADD
* Use measures

MUST NOT:

* Manually calculate YoY
* Simulate time shifts incorrectly

---

## 6. Validate Scaling

If requested:

* Absolute:

  * / 1,000,000
  * ROUND(...,1)
* Percent:

  * * 100
  * ROUND(...,1)

---

## 7. Validate Efficiency

Prefer:

* SUMMARIZECOLUMNS
* Minimal logic
* No unnecessary nesting

Reject ONLY if it impacts correctness.
